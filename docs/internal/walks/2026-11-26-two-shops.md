# Walk of two shops: the install check, one shared connection, a connection per shop — 2026-11-26

Internal record. A worker walked a store of two shops on `v3` (`91acd79`), on PrestaShop 8.2.8
(PHP 8.0.30, theme classic) and 9.2.0 (PHP 8.5.12, theme hummingbird): the install with two shops,
"One store in several versions" with one installation-wide Campaign Intelligence connection, the
change to separate stores, a connection per shop, and the change back, with capabilities 9 to 11
in each layout. The merchant's part ran through the admin screens in a headless browser, the
shopper's part through each shop's storefront in a browser, the background part through the tick
URL, and the engine, the Smaily and the subscription side on the mocks behind the egress guard.
Nothing in the module was changed.

| Part | 8.2.8 | 9.2.0 |
|---|---|---|
| `tests/ci/validate.sh` with `SHOPS=2` (console install, flashlight) | 10 of 12: **defect**, the module is not enabled in shop 2 | 10 of 12: the same defect |
| The walk (install from Module Manager, both layouts, capabilities 8 to 11) | 91 of 91 | 91 of 92: the one is a fault of the walk (section 7) |

**One defect found** (section 2): a console install in a store of two shops enables the module in
the default shop only. An install from Module Manager with "All shops" selected enables it in both.
No defect was found in the connections, the imports, the keys, the consent per shop, the
automations, the tracking, the attribution, the block or the feed.

## 1. How the walk ran

- **Shops.** One stack of this worktree, `ver2-walk` (port 8510), one lane at a time, each made
  from scratch (`down -v`): flashlight `9.2.0-nginx`, then `8.2.8-8.0-nginx`, the dev stack with
  `src/` mounted as the module's folder; debug mode on. Shop 1 "PrestaShop" at
  `http://localhost:8510`, shop 2 "Second shop" at `http://127.0.0.1:8510`, both in the default
  shop group, which does not share customers. All removed with `down -v` at the end.
- **Staging by script, not part of what is proven** (`build/walk-2shops/stage.php` and
  `tests/ci/second-shop.php`): multistore on and the second shop with the data of shop 1, as the
  back office's "Add new shop" imports it; two catalogs that overlap (products 1 to 8 in both
  shops, 9 to 18 in shop 1 alone, 19 in shop 2 alone: 18 and 9 products); four invented
  customers on `example.test`, two per shop, one subscribed and one with an order of 30 days
  (a copy of demo order 1) in each shop; demo orders 1 to 5 stay in shop 1; no outgoing mail; a
  throwaway payment module (`walkpay`, DEV_ENVIRONMENT 4b) in the container, never in the
  repository; the block on `displayHome` in both shops; the Smaily mock's workflows 11, 21 and 22;
  the engine mock's prefix for the next connection (`c7-`, then `c8-`) and, for shop 1's own
  connection, the engine store of the first one (one Smaily account, so one engine store).
- **Browser.** Headless Chromium through playwright-core 1.64: one context for the employee
  (Module Manager's install request, the Initial setup, Settings), a fresh context for every
  shopper, every request to another origin than the two shops refused. Scripts in
  `build/walk-2shops/` of the worktree (git ignores `build/`), results per lane in
  `out/results-<version>-walk.jsonl`, screenshots in `out/shots/`.
- **The tick.** Every background step ran through the tick's real URL with its token (masked),
  asked for inside the shop container with shop 1's host name, after the walk marked the named
  jobs due.
- **What reached the engine** is read from the engine mock's request log: every request carries
  the SHA-256 of its key, and each check names which connection a request came under.
- **Nothing left the machine.** The proxy's log at the end of the 9.2.0 lane: 74 tunnels to the
  engine mock, 67 to the Smaily mock (`walkmain`), 7 to the subscription mock, 2 probes of the
  guard; 131 refusals, all of modules the image ships and of PrestaShop itself
  (`mbo-api.prestashop.com`, `sentry.io`, `a.klaviyo.com`, `api.prestashop-project.org`,
  `api.github.com`). On 8.2.8: 67, 65 and 5 tunnels, 9 refusals. `check.sh` answered `guard
  active` at the end of each lane. No PHP-FPM crash line and no `core` file.

## 2. The install with two shops

**`tests/ci/validate.sh` with `SHOPS=2`** (new switch, DEV_ENVIRONMENT 6): the zip as flashlight
installs it, then the second shop, then the module uninstalled and installed again by the console
in that store of two shops. Ran on both versions with the same result:

| Check | 8.2.8 | 9.2.0 |
|---|---|---|
| The module installs in a store of two shops (console) | ok | ok |
| Module row 3.0.0, 30 hooks, 10 tables, schema version | ok | ok |
| The module is enabled with its 30 hooks in each of the 2 shops | **FAIL**: `ps_module_shop` holds shop 1 alone; the hooks are registered in both | **FAIL**, the same |
| Storefront, API client, shop 1's feed, the two cron doors | ok | ok |
| Shop 2's storefront answers 200 and its feed links to its own address | **FAIL**: the feed answers 404 (the module is off in shop 2) | **FAIL**, the same |

The unit and integration suite is skipped with `SHOPS=2`: in the first 9.2.0 run it ran in the
store of two shops, and 10 of its 2284 tests failed on the premise of one shop (the layout
question appears, the page scope names `shop-1`, a shop tree has two rows, and so on), and its
legacy fixtures' clean-up (`LegacyStore::removeSecondShop()`) deleted the store's own shop 2 and
switched multistore off. Without the switch the script passes 10 of 10 on both versions with the
edited script (2284 tests; 12214 and 12219 assertions).

**Install from Module Manager** (the walk, both versions): the request that Module Manager's
Install button sends, with "All shops" selected, in the employee's session.

| # | Check | 8.2.8 | 9.2.0 |
|---|---|---|---|
| i.0 | Two shops, multistore on, each its own address | pass | pass |
| i.1 | Module Manager installs the module ("Install action on module smailyforprestashop succeeded.") | pass | pass |
| i.2 | The module is enabled in both shops | pass | pass |
| i.3 | Its 30 hooks are registered in each shop | pass | pass |
| i.4 | 10 tables, the schema version; no connection, no account | pass | pass |
| i.5 | Each storefront answers 200; each shop's feed is RSS on its own address | pass | pass |

**The defect.** The main class sets `Shop::setContext(Shop::CONTEXT_ALL)` after
`parent::install()`, which enables the module only in the shops of the context it runs in. The
console (and flashlight's `INSTALL_MODULES_DIR`, which calls it) runs in the default shop, so shop
2 gets the hooks but no `ps_module_shop` row: nothing of the module runs on its storefront, and its
feed and cron doors answer 404. 2.2.0 has the same order. The fix is to set the context before
`parent::install()`; the main class changes only in the Stories that ARCHITECTURE 13 names, so it
is a follow-up.

## 7. Walk-tool faults (so that the counts can be trusted)

- **9.2.0, p3.c (shop 2's block): not passed, a fault of the walk.** The first run of the live
  changes loaded product 19, which shop 2 alone sells, in the default shop and saved it there:
  its shop-2 row came back inactive, not orderable, without a price. The walk repaired the row
  by SQL and changed the staging to load a product in a shop that holds it; shop 2's block then
  had no connection of its own left to ask (the change back to one store had run). It showed 19
  and 6 from the carried connection (l2.c), and on 8.2.8, with the corrected staging, p3.c
  passed for both shops.
- Checks that passed on a second reading or a second run, each recorded with the reason:
  s.4 (the first pattern stopped at the dot of "1.0.0"), o.4 (a single-language link read as a
  map of languages), c1.block (a tile carries two links), s.1 on 9.2.0 (the Dashboard asks for
  the cron line only after the setup), p3.i2 customers on 9.2.0 ("Run again" clicked by position
  after a card's button had hidden), p3.live on 9.2.0 (the staging fault above).
- The first storefront rounds on 9.2.0 asked for `index.php?controller=product`, which debug
  mode answers as a moved page without the page hooks (DEV_ENVIRONMENT 4b); their results were
  removed and the part ran again with the shop's own addresses (8.2.8's theme puts the category in
  a product's address, so the walk takes them from PrestaShop's `Link`).
- On 8.2.8 the first install request had no Symfony token (the back office lands on a legacy
  Dashboard address); the shop was not touched by it, and the install ran again with the token
  of Module Manager's page.
